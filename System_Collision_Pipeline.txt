## Collision Handling in MuseScore
This codemap explores how MuseScore prevents and resolves collisions between notation elements using horizontal spacing and vertical autoplacement. It traces the logic from high-level system layout down to fine-grained shape intersection tests. Key logic resides in HorizontalSpacing [1c] and Autoplace [2b].
### 1. Horizontal Collision Avoidance
Traces how MuseScore calculates horizontal gaps between segments using shapes and padding tables to prevent overlapping notation.

```text

```
### 1b. Space Against Previous Segments (`horizontalspacing.cpp:280`)

```text

```
### 1c. Calculate Min Horizontal Distance (`horizontalspacing.cpp:1296`)

```text

```
### 1d. Lookup Type-Based Padding (`horizontalspacing.cpp:1413`)
Looks up the base padding between two specific element types from the style-defined table.
```text
double padding = paddingTable.at(type1).at(type2);
```
### 1e. Determine Kerning Strategy (`horizontalspacing.cpp:1211`)
Determines if elements can 'kern' (tuck into each other) or must remain strictly separated.
```text

```
### 2. Vertical Autoplace (Skyline) Logic

### 2b. Get Staff Skyline (`autoplace.cpp:159`)

```text

```
### 2c. Measure Distance to Skyline (`autoplace.cpp:172`)
Calculates the minimum vertical distance required to clear the existing skyline.
```text

```
### 2d. Apply Vertical Shift (`autoplace.cpp:191`)

```text

```
### 2e. Update Skyline with New Item (`autoplace.cpp:195`)
Adds the newly placed element's shape to the skyline so subsequent items avoid it.
```text

```
### 3. Shape Intersection & Clearance Math
Traces the low-level geometry math used to detect overlaps between complex shapes (collections of rectangles).

Checks if two shapes clear each other vertically within their shared horizontal span.

### 3b. Range Intersection Test (`shape.h:197`)

It covers skyline lifecycle management [1a], chord and stem layout dependencies [2c], autoplace collision detection logic [3b], and the measure layout sequence [4b]. The "Golden Rule" of the Pipeline
If you want to keep this reactive state stable as you add more features (like slurs or beam groups), remember the order of operations we enforced in the engrave loop:

Resolve Beaming: Compute beam group associations first (logical structure).

Calculate Rhythmic Spacing: Build the "springs" to get the base x coordinates.

Calculate Preamble/Fixed Space: Account for clefs and keysigs so they don't shift.

Engrave & Stretch: Generate elements with the stretchRatio applied to rhythmic gaps only.

Run Collision Avoidance: Only after everything is positioned do you run the runSkylinePlacement to move things vertically.
